# Phase 3 — 인제스트 큐 설계 (마이그 026)

> **상태**: 설계 초안. **SQL 은 아직 적용하지 않았다** — 사용자 확인 대기.
> **선행 완료**: 샌드박스 하네스(111d05f) · 기준선 3포맷(0f365b8) · CPU 계측(ca6dae6).

## 0. 왜 큐가 필요한가

현행은 `upload_document` 가 202 를 주고 `BackgroundTasks` 로 9단계를 **한 번에** 돌린다.
Edge Functions 는 **요청당 CPU 2초**라 그 모델이 성립하지 않는다. 그래서 "작업 1건씩"
처리하는 큐 드리븐 상태 머신으로 바꾼다.

## 1. 실측으로 확정된 제약

| 항목 | 값 | 출처 |
|---|---|---|
| CPU 예산 | **2s / 요청** (유료로도 완화 안 됨) | Supabase Limits |
| 백그라운드 wall clock | 400s (Pro) | 〃 |
| PDF 텍스트+span | 페이지당 최대 **100.8ms** | Phase 0 S2 |
| **PDF vision 래스터화 + PNG** | 페이지당 최악 **443ms** | 2026-09-07 실측 |
| HWP / HWPX / DOCX / PPTX 파싱 | 72 / 1.5~27 / 10~72ms | Phase 0 S1·S4 |
| 메모리 | 상한 240MB, PDF 경로 24MB | Phase 0 S5 |

**작업 단위**: vision 렌더가 붙는 페이지는 **1~2p**, 텍스트만이면 최대 10p.
443ms × 4.5 = 2s 이므로 안전마진 50% 를 적용한 값이다.

## 2. 확장 설치 상태 (2026-09-07 실측)

```
설치됨   : pg_stat_statements, pg_trgm, pgcrypto, pgroonga@3.2.5,
           plpgsql, supabase_vault@0.3.1, uuid-ossp, vector@0.8.0
미설치   : pgmq, pg_cron, pg_net   ← 마이그 026 이 설치한다
설치 가능: pgmq@1.5.1, pg_cron@1.6.4, pg_net@0.20.0
```

`supabase_vault` 가 이미 있는 게 중요하다 — pg_cron 이 Edge Function 을 부를 때 쓸
service_role 키를 **SQL 에 평문으로 박지 않고** Vault 에서 읽을 수 있다.

## 3. 왜 `public` 래퍼가 필요한가

PostgREST 가 노출하는 스키마는 **`public`, `graphql_public` 뿐**이다(실측:
`pgmq_public.send` 호출 시 `PGRST106 Invalid schema`). Edge Function 은 supabase-js →
PostgREST 경로로 DB 를 쓰므로, `pgmq.*` 를 직접 못 부른다.

선택지는 둘이었다:

| | 방안 | 판단 |
|---|---|---|
| A | `public` 에 `SECURITY DEFINER` 래퍼 함수 | **채택** — 기존 Edge 코드가 전부 supabase-js 다 |
| B | Edge 에서 Postgres 직접 연결(deno-postgres) | 연결 풀·시크릿 관리가 따로 생긴다 |

A 를 쓰되 래퍼는 **service_role 에게만** 실행 권한을 준다. anon/authenticated 가 큐를
건드릴 수 있으면 안 된다.

## 4. 작업 메시지 스키마

```jsonc
{
  "job_id":  "uuid",      // ingest_jobs.id — 상태의 단일 출처
  "doc_id":  "uuid",
  "stage":   "extract",   // 9단계 중 하나
  "from":    0,           // 페이지/청크 범위 시작 (해당 stage 만)
  "count":   1,           // 처리 개수 — CPU 예산으로 정한다
  "attempt": 1
}
```

`ingest_jobs` 를 상태의 단일 출처로 둔다. 큐 메시지는 **무엇을 할지**만 담고,
진행 상태는 테이블이 갖는다(마이그 010 의 `stage_progress` 를 그대로 재사용).

## 5. 9단계 — 현행 순서 (실측)

```
extract → chunk → chunk_filter → content_gate → tag_summarize → load → embed → doc_embed → dedup
```

**계획서의 "8-stage" 는 틀렸다.** 실제로는 9개이고 `content_gate` 가 `chunk_filter` 뒤,
`load` 가 `embed` **앞**이다(2026-09-07 기준선 실측).

| 단계 | 분할 필요 | 근거 |
|---|---|---|
| extract | **예** — 페이지 단위 | vision 페이지 443ms |
| chunk · chunk_filter · content_gate | 아니오 | 텍스트 연산, 가볍다 |
| tag_summarize | 아니오 | LLM 호출 = I/O (CPU 미포함) |
| load | 배치 | 청크 upsert, 기존 `chunk_upsert_batch_size=50` |
| embed | 배치 | 임베딩 API = I/O. 배치 크기는 API 제한이 정한다 |
| doc_embed · dedup | 아니오 | 단발 |

**I/O 는 CPU 에 안 잡힌다**(Supabase 문서). 그래서 LLM·임베딩 호출이 많은 단계는
분할 압력이 낮고, **파싱·래스터화만 진짜 제약**이다.

## 6. 드레인 방식

```
pg_cron (초 단위 스케줄, 1.6.4 지원)
   └─ pg_net.http_post → Edge `ingest-worker`
        └─ public.ingest_queue_read(vt, qty) → 작업 처리 → ingest_queue_delete
```

- **visibility timeout(vt)**: 작업이 죽어도 vt 후 다시 보인다. Edge wall clock 400s 를
  넘지 않게 vt 를 그보다 크게 잡는다.
- **재시도**: pgmq 의 `read_ct` 가 시도 횟수다. 한도 초과분은 `pgmq.archive` 로 보내고
  `ingest_jobs.status='failed'` 로 마킹한다.
- **멱등성**: 같은 작업이 두 번 실행돼도 안전해야 한다(vt 만료 후 재배달 가능).
  각 단계가 **upsert 또는 조건부 쓰기**여야 한다 — 구현 시 단계별로 확인할 항목.

## 7. 아직 정하지 않은 것 (구현하며 실측으로)

- 드레인 주기와 동시 처리 수 — 큐 적체를 보고 조정
- `vt` 구체값 — 단계별 최장 wall clock 을 재고 결정
- 재시도 한도 — 현행 `attempts` 는 전부 1 이라 참고할 실적이 없다

## 8. 적용 절차 (사용자 실행)

마이그레이션은 **DB 스키마 변경**이라 확인 없이 적용하지 않는다.

1. Supabase Studio → SQL Editor → New query
2. `api/migrations/026_pgmq_ingest_queue.sql` 전문 붙여넣기 → Run
3. 검증 SQL(파일 하단 주석)로 확장·큐·함수 생성 확인

**되돌리기**: 같은 파일 하단의 롤백 SQL. 큐에 메시지가 남아 있으면 먼저 비운다.
