# Phase 2 — 읽기 경로 이관 (`/search` 중심)

> **전제**: Phase 1 완료 (2026-09-04). `/auth/*`·`/health` 는 이미 Edge 에서 돌고,
> Cloudflare 프록시가 경로별 전환 스위치 역할을 한다.
> **이 문서의 범위**: `/search` 상세 계획. `/answer`·`/stats`·`/me`·`/admin` 은 §8 에 개요만 둔다.

## 0. 착수 전 확정된 사실 (실측)

| 사실 | 값 | 근거 |
|---|---|---|
| **CPU 는 제약이 아니다** | 검색 1회 CPU **7.8~21.2ms** (Edge 예산 2,000ms 의 ~1%) | `measure_search_cpu.py` |

## 4. 비활성 기능을 어떻게 다룰 것인가 ← **여기가 이 플랜의 핵심 결정**

"지금 꺼져 있으니 안 옮긴다" 는 그대로 두면 **조용한 함정**이 된다.
운영자가 나중에 `JETRAG_RERANKER_ENABLED=true` 를 켜면 Railway 에서는 동작하고
Edge 에서는 **아무 일도 일어나지 않은 채 다른 순위**가 나온다. 로그도 안 남는다.

**방침: 옮기지 않되, 켜지면 시끄럽게 실패한다.**

```
포팅한 Edge 함수는 기동 시 미구현 토글이 켜져 있는지 확인하고,
켜져 있으면 500 + `{"detail": "이 기능은 Edge 로 아직 이관되지 않았습니다: JETRAG_RERANKER_ENABLED"}`
```

근거: Phase 1 에서 같은 종류의 위험을 두 번 만났다.
(`SUPABASE_` secret 이 **조용히** 건너뛰어진 것, 검색 토글 기본값이 곧 운영 동작인 것)
조용한 차이는 발견이 늦고, 발견돼도 원인 추적이 어렵다.

**미구현 목록은 `_shared/search/unsupported.ts` 한 곳에 둔다.** 나중에 그 기능을 이식하면
목록에서 한 줄을 지우는 것으로 활성화된다.

## 5. 이식 단위 분해 — `search()` 1,020줄을 어떻게 쪼개나

원칙: **각 단위가 독립적으로 원본 대조 가능해야 한다.** 그래야 Phase 1 에서 효과를 본
패리티 검사기를 그대로 쓸 수 있다. 순수 함수를 먼저, I/O 를 나중에.

| # | Deno 모듈 | 원본 | 성격 | 대조 방법 |
|---|---|---|---|---|
| 1 | `search/params.ts` | 진입 검증 + NFC | 순수 | 입력 → (정규화 질의, 오류) 대조 |
| 2 | `search/pgroonga.ts` | `_build_pgroonga_query`, `_strip_korean_particle` | 순수 | **질의 문자열 완전 일치** |
| 3 | `search/guards.ts` | `_is_cover_chunk`, `_is_toc_chunk` | 순수 | 청크 텍스트 → bool |
| 4 | `search/rrf.ts` | 3) 그룹·dedupe, 5) 정렬 | 순수 | RPC row 배열 → 정렬된 doc 목록 |
| 5 | `search/filters.ts` | 4) 메타 필터 4종 | 순수 | doc 배열 + 필터 → 통과 목록 |
| 6 | `search/snippet.ts` | `_make_snippet_with_highlights`, `synonym_inject` | 순수 | **스니펫 문자열 완전 일치** |
| 7 | `search/assemble.ts` | 7) 응답 조립 + relevance 정규화 | 순수 | 중간 상태 → `SearchResponse` JSON |
| 8 | `search/intent.ts` | `services/intent_router.py` | 순수 | 질의 → 신호 집합 |
| 9 | `search/mmr.ts` | `services/mmr.py` | 순수 | 벡터+점수 → 재정렬 |
| 10 | `search/meta_fast_path.ts` | `services/meta_filter_fast_path.py` | 순수 + DB | plan 판정은 순수 → 대조, DB 부분은 통합 |
| 11 | `search/embed.ts` | `bgem3_hf_embedding` + `embed_query_cache` | I/O | 같은 질의 → 같은 벡터(캐시 포함) |

| 13 | `search/metrics.ts` | `services/search_metrics.py` | I/O | 기록된 row 대조 |
| 14 | `api-search/index.ts` | `search()` 흐름 | 오케스트레이션 | **엔드투엔드 응답 대조** |

1~9 는 **순수 함수라 Python 과 직접 대조**할 수 있다. 이게 전체 위험의 대부분을 덮는다.
10~13 은 실제 DB·API 를 타므로 통합 대조로 넘긴다.

## 6. 원본 대조 계획 — Phase 1 의 반성 반영

Phase 1 에서 플랜 초안 오류가 **5건** 나왔고 전부 코드를 쓰기 전에 잡혔어야 했다
(`JETRAG_DEFAULT_USER_ID` 접두어, 불리언 fallback, 배치 상한, `LEGACY_ORIGIN` 호스트,
`/stats/overview` 기대값). 원인은 같다 — **플랜을 쓸 때 원본을 안 열었다.**

그래서 Phase 2 는 각 Task 의 **Step 1 을 "원본 열고 계약 받아쓰기"** 로 고정한다:

```
Step 1  원본 함수를 읽고 계약을 표로 옮긴다 (입력·출력·경계·기본값)
Step 2  그 표를 그대로 패리티 케이스로 만든다 (실패하는 상태)
Step 3  구현
Step 4  패리티 통과 + **음성 대조** (일부러 틀리게 만들어 검사기가 잡는지)
Step 5  커밋
```

Step 4 의 음성 대조는 선택이 아니다. Phase 1 에서 cors 패리티가 `Vary` 버그를
**못 잡았고**, 사각지대를 메운 뒤에야 잡혔다.

### Task 2.8 에서 나온 것 — **원본 버그 1 건, 전환 선행 1 건**

**(라) 운영에서 MMR 은 도달 불가능한 코드다.**
`search.py` 3) 단계의 `for r in rpc_rows: doc_id = r["doc_id"]`(1286 행)가 **함수 파라미터
`doc_id` 를 덮어쓴다.** 그 뒤 5) 단계 MMR 게이트가 `doc_id is None`(1458 행)을 보므로,
rpc_rows 가 비지 않는 한 항상 False 다. 두 행 사이에 `doc_id` 재대입은 없다(전 구간 확인).

실측(2026-09-05): T1 이 발화하고 문서가 5~8 건인 질의 **7 개 전부에서 `mmr.rerank` 호출 0 회**.
원본 소스에도 이 shadowing 을 아는 주석이 있지만(1510~1513 행), 그건 청크 cap 판정을
`rpc_top_k` 로 재구성하는 대목이고 **MMR 게이트는 고쳐지지 않았다.**

Edge 포팅은 처음에 파라미터 `docId` 를 그대로 써서 **MMR 을 되살렸고**, 그래서 cross-doc
질의의 순위가 갈렸다(패리티가 잡았다). 이식은 동작을 맞추는 일이므로 **덮어쓰기까지
재현**해 두었다 — 나중에 원본이 고쳐지면 패리티가 그 차이를 잡는다.

→ **사용자 결정 필요**: ① 지금은 운영과 동일하게(MMR 꺼짐) 두고 이관을 끝낸 뒤,
별도 작업으로 Railway·Edge 양쪽을 함께 고친다 ② 지금 고친다(= 운영 순위가 바뀌므로
골든셋 재측정이 따라붙는다). 기본은 ①.

**(마) meta fast path 는 전환의 하드 선행 조건이다.**
ENV 토글이 아니라 항상 켜진 분기라 `unsupported.ts` 로 막을 수 없다. 미이식 상태로
전환하면 fast path 질의가 Edge 에서 조용히 RAG 경로로 처리된다.
패리티 케이스 23 건 중 **3 건이 이 이유로 건너뛰어졌다**(`한 단어`/`offset 1`/`offset 범위 밖`).
→ **Task 2.6 을 2.9 앞에 둔다.**

### Task 2.7 에서 나온 것 — **전환 전에 결정해야 하는 2 건**

**(가) `/stats.search_slo` 가 전환과 동시에 눈이 먼다. → 해결 (2026-09-05)**
표본 출처를 `search_metrics_log` 로 옮겼다. `JETRAG_SLO_SOURCE` 로 `ring` 회귀 가능하고,
응답에 `source` 필드(`db`/`ring`/`ring_fallback`)를 노출해 어디서 읽었는지 드러낸다.
같은 표본에서 두 경로가 완전히 일치함을 500 행으로 확인
(`verify_slo_source_parity.py`, p50=183 p95=1828). 아래는 당시 문제 기술.

`search_metrics.py` 는 DB write-through 와 **별도로** 프로세스 안 ring buffer 를 두고,
`/stats` 의 `search_slo` 가 그걸 읽는다(`stats.py:246`). Edge 는 isolate 가 휘발성이라
그 구조가 성립하지 않는다. `/search` 만 Edge 로 넘기면 Railway 프로세스의 ring 에는
아무것도 안 쌓이므로 **`/stats.search_slo` 가 계속 0 을 보고한다** — 매일 02:00 UTC cron
(`monitor-search-slo.yml`)이 보는 값이 바로 그것이다. 이식 품질과 무관하게 **전환 자체가
만드는 회귀**다.

대체 경로는 있다 — `search_metrics_log` 에 `get_search_slo()` 가 계산하는 필드가 전부 있고
**17,378 행이 쌓여 있다**(2026-09-05 실측). `/stats` 를 DB 집계로 바꾸면 검색이 어디서
돌든 지표가 유지된다. 어차피 `/stats` 를 Edge 로 옮길 때도 필요한 작업이라 미룰수록 비싸다.
→ **Task 2.9 전에 처리한다.**

**(나) DeepInfra 임베딩은 결정적이지 않다.**
같은 텍스트를 4 회 불러 보면 일부 호출에서 1024 성분이 전부 다르고, 그때 자기 코사인은
**0.999999** 수준이다(2026-09-05 실측). HF 는 3 회 모두 완전 일치했다. 운영이 어느
제공자를 쓰든 `embed_query_cache` 가 첫 호출 결과를 영구 보관하므로 **반복 질의는
안정적**이지만, **캐시에 없는 질의는 실행마다 dense 순위가 미세하게 달라질 수 있다.**
→ §9 골든셋 비교는 캐시가 채워진 상태에서 돌리거나, 그 사실을 결과에 명시한다.

**(다) 운영 제공자 값이 미확인.** Railway 에 `JETRAG_EMBED_PROVIDER` 가 **설정돼 있다**는

  포팅 중 임의로 고치지 않았다. 2.6 에서 ① 그대로 재현 ② 필터를 넘겨 고침 중 택일한다.

### 러너가 고장나 있었다 — 고쳤다

baseline 을 찍으려고 돌렸더니 **전 지표가 0.000** 이었다. 검색은 정상 동작하는데
`predicted top-5` 가 전부 비어 있었다.

원인: `_call_search()` 가 `current_user` 를 넘기지 않아 `search()` 의 기본 사용자
(`LEGACY_DEFAULT_USER` = `00000000-...-0001`)로 검색된다. D1 사용자 격리 이후 문서는 전부
owner(`2af8fca5-...`) 소유라 **그 사용자로는 한 건도 안 잡힌다.** 실측 대조:

```
러너와 동일 (current_user 미전달) → items=0, dense=0, sparse=0, fused=0
owner 로 전달                    → items=1, dense=35, sparse=38, fused=50
```

즉 이 회귀 스위트는 **줄곧 조용히 R@10 0.000 만 내고 있었다.** Phase 4 데이터 이관으로
문서 소유자가 바뀐 시점부터로 보인다.

수정: `--user-id` 옵션 추가(기본값 `OWNER_USER_ID` ENV). 둘 다 없으면 **경고를 띄운다** —
조용히 0 을 내지 않도록. 양쪽 경로를 실제로 돌려 확인했다.

### 여기에 **손봐야 할 것**이 하나 더 있다

러너가 `search()` 를 **in-process 로 직접 호출**한다(문서 주석에 명시). 그래서 **Edge 버전을
그대로는 못 잰다.** Task 2.8 전에 러너에 HTTP 모드를 추가해야 한다:

```
--endpoint <URL>  주면 in-process 대신 HTTP 로 호출 (Edge/Railway 어느 쪽이든 지정 가능)
```

그러면 **같은 133행을 Railway 와 Edge 양쪽에 돌려 지표를 나란히 비교**할 수 있다.
"회귀 0" 을 절대값이 아니라 **양쪽 차이**로 판정하는 게 정확하다 — 골든셋 절대 지표는
데이터 상태에 따라 흔들리지만, 같은 시점 두 구현의 차이는 이식 정확도만 반영한다.
