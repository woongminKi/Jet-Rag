# Phase 2 — 읽기 경로 이관 (`/search` 중심)

> **전제**: Phase 1 완료 (2026-09-04). `/auth/*`·`/health` 는 이미 Edge 에서 돌고,
> Cloudflare 프록시가 경로별 전환 스위치 역할을 한다.
> **이 문서의 범위**: `/search` 상세 계획. `/answer`·`/stats`·`/me`·`/admin` 은 §8 에 개요만 둔다.

## 0. 착수 전 확정된 사실 (실측)

| 사실 | 값 | 근거 |
|---|---|---|
| **CPU 는 제약이 아니다** | 검색 1회 CPU **7.8~21.2ms** (Edge 예산 2,000ms 의 ~1%) | `measure_search_cpu.py` |
| wall 의 83~92% 는 I/O 대기 | 임베딩 API + DB RPC | 동일 |
| `limit` 10→50 도 CPU 거의 불변 | 9.5~18.6ms | 융합 후보가 ~50 에서 포화 |
| 앱 코드에 CPU 핫스팟 없음 | cProfile tottime 전부 0.000s | 동일 |
| `answer` 는 동기 호출, wall 7.2~8.7s | Edge 초기 응답 150s 대비 17배 여유 | Step 0 |

**결론: 설계 문제가 아니라 이식량 문제다.** 팬아웃·비동기화 같은 구조 변경은 불필요하다.

## 4. 비활성 기능을 어떻게 다룰 것인가 ← **여기가 이 플랜의 핵심 결정**

"지금 꺼져 있으니 안 옮긴다" 는 그대로 두면 **조용한 함정**이 된다.
운영자가 나중에 `JETRAG_RERANKER_ENABLED=true` 를 켜면 Railway 에서는 동작하고
Edge 에서는 **아무 일도 일어나지 않은 채 다른 순위**가 나온다. 로그도 안 남는다.

**방침: 옮기지 않되, 켜지면 시끄럽게 실패한다.**

```
포팅한 Edge 함수는 기동 시 미구현 토글이 켜져 있는지 확인하고,
켜져 있으면 500 + `{"detail": "이 기능은 Edge 로 아직 이관되지 않았습니다: JETRAG_RERANKER_ENABLED"}`
```

근거: Phase 1 에서 같은 종류의 위험을 두 번 만났다.
(`SUPABASE_` secret 이 **조용히** 건너뛰어진 것, 검색 토글 기본값이 곧 운영 동작인 것)
조용한 차이는 발견이 늦고, 발견돼도 원인 추적이 어렵다.

**미구현 목록은 `_shared/search/unsupported.ts` 한 곳에 둔다.** 나중에 그 기능을 이식하면
목록에서 한 줄을 지우는 것으로 활성화된다.

## 5. 이식 단위 분해 — `search()` 1,020줄을 어떻게 쪼개나

원칙: **각 단위가 독립적으로 원본 대조 가능해야 한다.** 그래야 Phase 1 에서 효과를 본
패리티 검사기를 그대로 쓸 수 있다. 순수 함수를 먼저, I/O 를 나중에.

| # | Deno 모듈 | 원본 | 성격 | 대조 방법 |
|---|---|---|---|---|
| 1 | `search/params.ts` | 진입 검증 + NFC | 순수 | 입력 → (정규화 질의, 오류) 대조 |
| 2 | `search/pgroonga.ts` | `_build_pgroonga_query`, `_strip_korean_particle` | 순수 | **질의 문자열 완전 일치** |
| 3 | `search/guards.ts` | `_is_cover_chunk`, `_is_toc_chunk` | 순수 | 청크 텍스트 → bool |
| 4 | `search/rrf.ts` | 3) 그룹·dedupe, 5) 정렬 | 순수 | RPC row 배열 → 정렬된 doc 목록 |
| 5 | `search/filters.ts` | 4) 메타 필터 4종 | 순수 | doc 배열 + 필터 → 통과 목록 |
| 6 | `search/snippet.ts` | `_make_snippet_with_highlights`, `synonym_inject` | 순수 | **스니펫 문자열 완전 일치** |
| 7 | `search/assemble.ts` | 7) 응답 조립 + relevance 정규화 | 순수 | 중간 상태 → `SearchResponse` JSON |
| 8 | `search/intent.ts` | `services/intent_router.py` | 순수 | 질의 → 신호 집합 |
| 9 | `search/mmr.ts` | `services/mmr.py` | 순수 | 벡터+점수 → 재정렬 |
| 10 | `search/meta_fast_path.ts` | `services/meta_filter_fast_path.py` | 순수 + DB | plan 판정은 순수 → 대조, DB 부분은 통합 |
| 11 | `search/embed.ts` | `bgem3_hf_embedding` + `embed_query_cache` | I/O | 같은 질의 → 같은 벡터(캐시 포함) |
| 12 | `search/rpc.ts` | mode 별 RPC 호출 | I/O | 같은 인자 → 같은 row 집합 |
| 13 | `search/metrics.ts` | `services/search_metrics.py` | I/O | 기록된 row 대조 |
| 14 | `api-search/index.ts` | `search()` 흐름 | 오케스트레이션 | **엔드투엔드 응답 대조** |

1~9 는 **순수 함수라 Python 과 직접 대조**할 수 있다. 이게 전체 위험의 대부분을 덮는다.
10~13 은 실제 DB·API 를 타므로 통합 대조로 넘긴다.

## 6. 원본 대조 계획 — Phase 1 의 반성 반영

Phase 1 에서 플랜 초안 오류가 **5건** 나왔고 전부 코드를 쓰기 전에 잡혔어야 했다
(`JETRAG_DEFAULT_USER_ID` 접두어, 불리언 fallback, 배치 상한, `LEGACY_ORIGIN` 호스트,
`/stats/overview` 기대값). 원인은 같다 — **플랜을 쓸 때 원본을 안 열었다.**

그래서 Phase 2 는 각 Task 의 **Step 1 을 "원본 열고 계약 받아쓰기"** 로 고정한다:

```
Step 1  원본 함수를 읽고 계약을 표로 옮긴다 (입력·출력·경계·기본값)
Step 2  그 표를 그대로 패리티 케이스로 만든다 (실패하는 상태)
Step 3  구현
Step 4  패리티 통과 + **음성 대조** (일부러 틀리게 만들어 검사기가 잡는지)
Step 5  커밋
```

Step 4 의 음성 대조는 선택이 아니다. Phase 1 에서 cors 패리티가 `Vary` 버그를
**못 잡았고**, 사각지대를 메운 뒤에야 잡혔다.

### 여기에 **손봐야 할 것**이 하나 있다

러너가 `search()` 를 **in-process 로 직접 호출**한다(문서 주석에 명시). 그래서 **Edge 버전을
그대로는 못 잰다.** Task 2.8 전에 러너에 HTTP 모드를 추가해야 한다:

```
--endpoint <URL>  주면 in-process 대신 HTTP 로 호출 (Edge/Railway 어느 쪽이든 지정 가능)
```

그러면 **같은 133행을 Railway 와 Edge 양쪽에 돌려 지표를 나란히 비교**할 수 있다.
"회귀 0" 을 절대값이 아니라 **양쪽 차이**로 판정하는 게 정확하다 — 골든셋 절대 지표는
데이터 상태에 따라 흔들리지만, 같은 시점 두 구현의 차이는 이식 정확도만 반영한다.

## 10. 위험과 미검증

1. **`meta_filter_fast_path` 가 실제로 얼마나 발화하는지 모른다.** 440줄인데 운영 표본에서
   한 번도 안 탔다. 발화 빈도를 먼저 재고(골든셋 133행을 돌려 보면 나온다) 이식 우선순위를 정한다.
2. ~~`evals/` 골든셋 확인~~ → §9 에서 확인 완료.
3. ~~`008 split RPC` 적용 여부~~ → **적용 확인.** 코드가 `search_dense_only` ·
   `search_sparse_only` · `search_hybrid_rrf` 를 부르고, 운영 응답이 dense/sparse 를 분리해
   돌려준다(`dense_hits: 14, sparse_hits: 31`). **RPC 자체는 Postgres 안에 있어 이관 대상이 아니다** —
   Edge 도 같은 함수를 부른다.
4. **`search_metrics` 동기 기록** — 응답을 붙잡는다(누적 0.050s). Edge 에서는
   `EdgeRuntime.waitUntil` 로 응답 뒤로 빼되, **그 자체가 동작 변경**이므로 work-log 에 남긴다.
5. Deno 쪽 CPU 는 아직 안 쟀다. Python 21.2ms 가 Deno 에서 몇 배가 되든 예산의 1~5% 지만,
   Task 2.8 에서 `spike` 하네스로 재확인한다(하네스는 재배포해 뒀다).
6. **골든셋 지표의 현재 baseline 을 아직 안 찍었다.** Task 2.1 착수 전에 Railway 기준값을
   한 번 기록해 둬야 나중에 "회귀 0" 을 주장할 수 있다.
