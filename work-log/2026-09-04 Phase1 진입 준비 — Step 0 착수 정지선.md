## 0-3 — `answer` 응답 상한 (해소)

플랜 §5 의 미결 결정: "LLM 응답이 Edge 초기 응답 150s 를 넘는가".

`answer` 는 **동기 호출**이다(`answer.py:18` — "Q6 동기 호출, streaming 은 v1.5 이후").
운영 엔드포인트를 3회 호출해 실측:

| 질의 | `took_ms` | wall |
|---|---|---|
| 문서 핵심 요약 | 8,597 | 10.28s |
| 세무 판결 요지 | 7,171 | 7.68s |
| 데이터센터 신청 자격 | 8,747 | 9.46s |

→ **150s 제한은 문제가 아니다.** `EdgeRuntime.waitUntil` + 폴링 설계는 **불필요**.
Phase 2 는 평범한 동기 Edge Function 으로 간다.

### 다만 질문이 하나 옮겨갔다 — wall 이 아니라 CPU 다

위 8.6s 의 대부분은 Gemini 대기(I/O)이고, **Edge 의 2s 제한은 CPU 시간**이다.
즉 150s 는 통과했지만 진짜 관문은 "검색·리랭크·프롬프트 구성의 CPU 몫이 2s 안인가"로 바뀐다.

`search_metrics_log` 최근 1,000건 (마지막 기록 2026-07-19):

| 지표 | 값 |
|---|---|
| 최소 / 중앙 | 84ms / **182ms** |
| p90 / p99 | 818ms / **3,089ms** |
| 최대 | **42,106ms** |
| 2,000ms 초과 | 25/1,000 = **2.5%** |

**이 값은 wall clock 이라 그대로 CPU 로 읽으면 안 된다.** 임베딩 API·DB RPC 왕복이 포함돼
있어 42s 짜리는 외부 API 지연일 가능성이 높다. 지금 가진 계기로는 **분해가 안 된다**.

→ **Phase 2 진입 첫 작업은 검색 경로의 CPU 몫 실측**으로 잡는다. Phase 0 하네스와 같은
방식(동기 블록만 `measure()` 로 감싸 배포 후 호출)이면 바로 나온다.
샘플이 1.5개월 전 것이라는 점도 같이 기록해 둔다 — 그 사이 트래픽이 거의 없었다.
