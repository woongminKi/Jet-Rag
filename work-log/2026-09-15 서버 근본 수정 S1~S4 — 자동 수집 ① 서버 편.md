## 3. Task 3 — precheck

- `_shared/documents/precheck.ts`: `parsePrecheckBody`(배열·1~500·hex64·소문자 정규화·dedup) + `precheckHashes`(본인·미삭제·`in`) → `existing / failed / new`.
- 프록시 `routes.js` 에 `[/^\/documents\/precheck$/, "api-documents", POST]` 를 GET 전용 `{id}` 규칙 **앞**에 추가. `MIGRATED_METHOD_PATHS` 엔 넣지 않음(Edge 전용 라우트라 FastAPI 경로 fixture 테스트가 깨짐).
- **리뷰에서 잡힌 것 (수정 완료)**: **Critical** — 500개 해시를 `in` 필터로 보내면 요청 라인이 **33,626B**(n=100 은 6,826B)라 게이트웨이 8KB 헤더 버퍼에서 414. → `IN_CHUNK=100` 으로 끊어 조회. 테스트가 필터 인자를 안 잡아 테넌트 격리가 미고정 → 인자 캡처·단언. 250개 → `[100,100,50]` 청크 테스트. E2E 스크립트가 상태를 안 봐서 거짓 통과 가능 → 단계별 판정 + exit code.
- `GET /documents/precheck` 는 405 가 아니라 404(문서 id 로 해석). 플랜의 삽입 위치를 따른 결과이며 reingest 블록과 관행이 다름 — 기록만.

### 사고 경위

1. 재인제스트는 **청크를 먼저 지우고** 다시 만든다. SK 보고서(5월 Railway 처리, 청크 25,831)를 재인제스트했다.
2. Edge `extract` 는 152 창(28분)으로 끝났으나 `chunk` 단계는 추출물 20MB 를 한 태스크에서 처리하는 설계라 3회 연속 런타임 kill(ingest_logs 에 종료 시각·오류 없음). 재시도 한도 초과 → `failed`. **총 청크 37,081 → 11,259.** 골든셋에 SK 질의가 있어 검색 회귀.
3. 이는 이관 때 재지 않은 Edge 제약(chunk 단계 창 처리 불가)이 처음 드러난 것. 신규 대형 PDF 업로드에서도 같은 실패가 난다 → **P1 후속: chunk 단계 창 처리/스트리밍**.
4. 복구: 레거시 Python 파이프라인(`api/app`)을 로컬에서 운영 DB 로 직접 실행. 1차는 `JETRAG_EMBED_PROVIDER` 미지정으로 HF 401 → 파이프라인이 청크를 롤백. 2차는 DeepInfra 지정으로 재실행 (아래 결과).
5. 교훈은 메모리 `jetrag_edge_chunk_large_doc_hazard.md` 에 고정: **운영 문서를 측정 목적으로 재인제스트하지 않는다.**

## 6. 결정·발견 (사용자 미확인 항목 포함)

- **스펙 정정**: `max_documents` 는 이메일 경로만이 아니라 `rate_limit.ts` 경유로 웹 업로드에도 걸려 있었다(7/19 기록의 갭은 이미 닫혀 있었음). 스펙 §2 표에 정정 기록.
- **DDL 적용 경로**: `supabase db query --linked -f <파일>` 이 동작한다. 사용자 SQL Editor 절차 없이 마이그를 적용했다(스펙에서 승인된 마이그 030·031 범위 안).
- **CORS DELETE 허용**: 원본 FastAPI 와 의도적으로 다르다. 대조 하네스가 `Access-Control-Allow-Methods` 를 비교하면 갈린다 — Railway 가 없으므로 실질 영향 0.
- **23514 → 422**: 마이그 031 적용 전까지 `pc-agent` 채널 실제 신규 업로드는 422 `code:"channel"` 이다(스모크는 중복 파일이라 이 경로를 안 탔다).
