### 사고 경위

1. 재인제스트는 **청크를 먼저 지우고** 다시 만든다. SK 보고서(5월 Railway 처리, 청크 25,831)를 재인제스트했다.
2. Edge `extract` 는 152 창(28분)으로 끝났으나 `chunk` 단계는 추출물 20MB 를 한 태스크에서 처리하는 설계라 3회 연속 런타임 kill(ingest_logs 에 종료 시각·오류 없음). 재시도 한도 초과 → `failed`. **총 청크 37,081 → 11,259.** 골든셋에 SK 질의가 있어 검색 회귀.
3. 이는 이관 때 재지 않은 Edge 제약(chunk 단계 창 처리 불가)이 처음 드러난 것. 신규 대형 PDF 업로드에서도 같은 실패가 난다 → **P1 후속: chunk 단계 창 처리/스트리밍**.
4. 복구: 레거시 Python 파이프라인(`api/app`)을 로컬에서 운영 DB 로 직접 실행. 1차는 `JETRAG_EMBED_PROVIDER` 미지정으로 HF 401 → 파이프라인이 청크를 롤백. 2차는 DeepInfra 지정으로 재실행 (아래 결과).

### 2차 장애 — dense/hybrid 검색 500 (복구 직후)

- 증상: `/search` hybrid·dense 가 9~20s → Edge 500. sparse 만 정상. 캐시 워밍 6회 반복해도 회복 안 됨.
- 원인(실측): `search_dense_only`·`search_hybrid_rrf` 의 `(flags->>'filtered_reason') IS NULL` 조건을 planner 가 **185행**으로 추정(실제 21,920). LIMIT 50 을 채우려면 HNSW 의 27% 를 훑어야 한다고 보고 **Seq Scan + top-N 정렬**(37k 벡터 detoast, TOAST 194MB) 선택. `shared_buffers` 224MB 인 Micro 에서 TOAST 가 캐시에 있던 동안은 P95 1.7s 로 보였고(잠재 결함), 25,806 청크 재적재로 캐시가 밀리자 장애로 드러남. `enable_seqscan=off` 로도 window 함수 때문에 HNSW 를 못 탐(idx_chunks_doc 루프 16s).
- 수정: **마이그 033** — `CREATE INDEX CONCURRENTLY idx_chunks_filtered_reason ON chunks ((flags->>'filtered_reason'))` + ANALYZE. 식 통계가 생겨 추정 21,888 → HNSW 사용. 함수 13.7s → **1.21s**, API hybrid 500 → **1.4s**, dense 1.0s.
- 남은 것: `hnsw.ef_search` 40 이라 top_k 50 요청에 dense 후보 ~25개(이전 Seq Scan 은 50개 정확). 100 으로 올리면 50개지만 15s. `hnsw.iterative_scan=relaxed_order` 실측이 후속 과제.
- 골든셋 스모크(`golden_batch_smoke.py`, golden_v2 120행 hybrid): **top-1 93/120 (77.5%) · top-3 101/120 (84.2%) · p95 1,231ms**. 같은 형식의 이전 기록이 없어 직접 비교 불가(7/19 는 182행 기준 0.7966). dense 후보 축소 영향 가능성 → ef_search 후속과 함께 재측정.
