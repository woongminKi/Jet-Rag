## 2. 지금 트래픽이 어떻게 흐르는가

```
브라우저 (jetrag.woong-s.com)
   │  credentials: 'include' — .woong-s.com 쿠키
   ▼
jetrag-api.woong-s.com  ← Cloudflare (오렌지 구름, Worker route /*)
   │
   ├─ /auth/*  /health ──────────► Supabase Edge  api-account
   └─ 그 외 전부 ────────────────► Railway  jet-rag-production.up.railway.app
```

전환 스위치는 `workers/api-proxy/src/routes.js` 의 `ROUTES` 배열이다.
**한 줄 추가 = 그 경로만 Supabase 로, 한 줄 삭제 = 즉시 Railway 복귀.**

롤백 수단이 두 겹이다:
1. `ROUTES` 에서 해당 줄 삭제 후 `wrangler deploy` — 경로 단위
2. Cloudflare DNS 에서 `jetrag-api` 를 **회색 구름**으로 — 전체, 즉시

## 3. 검증 방식 — 단위 테스트만으로는 부족했다

각 모듈마다 **Python 원본과 같은 입력을 넣고 결과를 대조하는 검사기**를 따로 만들었다
(`api/scripts/verify_*_parity.py`, 5종). 단위 테스트는 "내가 이해한 계약" 을 고정할 뿐
**원본과 같다는 증명이 아니기** 때문이다.

이 방식이 실제로 잡은 것:

| 무엇 | 어디서 |
|---|---|
| `DEFAULT_USER_ID` 에 `JETRAG_` 접두어를 붙인 오기 | config 패리티 (음성 대조에서 FAIL 2) |
| base64 padding 계산이 공백 유무로 갈리는 문제 | cookie_token 패리티 |
| `//host` 형태를 Python 은 netloc 으로 보는데 JS 는 던짐 | cookie_token 패리티 |
| `aud` **누락**과 **불일치**를 갈라야 함 | jwt 단위 테스트 |
| `Vary` 를 덮어쓰는 버그 | cors 패리티 — **사각지대를 메운 뒤에야** 잡힘 |

**검사기도 양성·음성 양쪽에서 돌려야 한다.** cors 패리티는 처음에 `Vary` 버그를 못 잡았다 —
응답에 이미 `Vary` 가 있는 케이스가 없었기 때문이다. `/vary` 라우트를 추가하고 나서야
`py='Accept-Encoding, Origin' ts='Origin'` 으로 잡혔다.

## 5. 플랫폼 제약 — 배포해 봐야 드러난 것

1. **Edge 는 `SUPABASE_` 로 시작하는 secret 을 거부한다.**
   `Env name cannot start with SUPABASE_, skipping` 으로 **조용히 건너뛴다**(명령은 성공으로 끝난다).
   플랜은 `SUPABASE_JWT_ALGORITHM`·`SUPABASE_JWKS_URL` 을 그대로 옮길 수 있다고 전제했는데 불가능하다.
   → `config.ts` 가 **원래 이름 먼저, 없으면 `JETRAG_` 별칭** 순으로 읽게 했다.
   값을 유도하지 않은 이유: ENV 가 비었을 때 Python 은 실패하고 Edge 는 성공해 조용히 갈린다.

2. **함수 안에서 보이는 `pathname` 은 `/<함수명>/...`** 다.
   `/functions/v1/api-account/health` → 함수가 보는 값은 **`/api-account/health`**.
   `/functions/v1/<함수명>` 을 뗄 거라 짐작했다가 전 경로 404 가 났고, 경로를 덤프해서 고쳤다.

3. **로컬 workerd 가 `compatibility_date` 를 2026-05-03 까지만 지원한다.**
   더 최신 날짜를 쓰면 배포는 되는데 `wrangler dev` 가 안 떠 **배포 전 검증이 막힌다.**
   구름을 켠 뒤에야 버그를 알게 되면 API 전체가 1101 이 되므로 날짜를 낮췄다.

4. **`wrangler login` 은 이 세션에서 안 된다.** 120초 넘는 명령이 백그라운드로 가면
   `isInteractive: false` 가 되어 OAuth 대기가 깨진다(`request_forbidden`). 사용자 터미널에서 실행해야 한다.

## 10. 추가 — 검색 경로 CPU 몫 실측 (§7-1 해소)

Phase 2 의 성패가 걸린 수치라 먼저 쟀다. `time.process_time()`(CPU) 과 `time.monotonic()`(wall) 을
같이 재서 **I/O 대기를 걷어낸 몫**을 본다. 실제 DB·임베딩 API 를 태운 값이다.

| 질의 | 결과 | dense | sparse | fused | wall | **CPU** | CPU 비중 |
|---|---|---|---|---|---|---|---|
| 짧은 질의 | 5 | 14 | 31 | 45 | 103.8ms | **12.8ms** | 12.3% |
| 자연어 질의 | 4 | 33 | 32 | 50 | 124.7ms | **21.2ms** | 17.0% |
| 긴 자연어 질의 | 9 | 25 | 25 | 50 | 140.3ms | **15.6ms** | 11.1% |
| 문서유형어 혼합 | 3 | 23 | 28 | 50 | 133.2ms | **12.8ms** | 9.6% |
| 영문 질의 | 6 | 25 | 25 | 50 | 95.7ms | **7.8ms** | 8.2% |

`limit` 을 10 → 50 으로 올려도 CPU 는 9.5~18.6ms 로 거의 변하지 않는다(융합 후보가 ~50 에서
포화라 후처리량이 그대로다).

**판정: CPU 는 제약이 아니다.** 최대 21.2ms 로 Edge 예산 2,000ms 대비 **약 94배 여유**다.
wall 의 나머지 83~92% 는 임베딩 API·DB RPC 대기라 Edge CPU 예산에 잡히지 않는다.

cProfile 로 귀속을 봤지만 `app/` 코드의 자체 CPU(tottime)가 전부 **0.000s** — 해상도에 안 잡힐
만큼 작다. 핫스팟이 없고 10~20ms 는 httpx·pydantic 처리에 분산돼 있다.

### 측정이 대표성을 갖는지 확인한 것

- **리랭커·질의분해가 안 켜진 상태**로 쟀다. 운영 엔드포인트도 같은 응답을 준다
  (`reranker_used: false`, `decomposition_fired: false`) — 로컬만의 상황이 아니다.
- 운영 `took_ms` 는 1,275ms 로 로컬(~107ms)보다 훨씬 크지만 그건 **wall** 이다.
  Railway 가 US West 라 Supabase·임베딩 API 왕복이 길어진 것으로 보인다.

### 도중 잡은 계측기 오류

처음 측정에서 **전 질의가 0건**으로 나왔다. 응답 필드가 `results` 가 아니라 `items` 인데
잘못 읽은 것이었다 — 검색 자체는 정상이었다. 그대로 뒀으면 "후처리 CPU 가 거의 없다" 는
**맞는 결론을 틀린 근거로** 낼 뻔했다. `dense_hits`/`sparse_hits`/`fused` 를 같이 찍어
전 경로가 실제로 돌았는지 확인하도록 고쳤다.

### Phase 2 로 넘기는 메모

`search_metrics.py:_persist_to_db_sync` 가 검색마다 **동기로** DB 에 지표를 쓴다(누적 0.050s).
CPU 는 아니지만 응답을 붙잡는다 — Edge 에서는 `EdgeRuntime.waitUntil` 로 응답 뒤로 빼는 게 낫다.
